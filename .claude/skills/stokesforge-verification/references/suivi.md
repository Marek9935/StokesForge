# The tracking page (#413, #441)

Read from step 6 to 8 of `stokesforge-verification`, and by `stokesforge-feature` at the start and at the trial. One local page, served on this PC by `scripts/suivi.py serve` (`http://127.0.0.1:8441/`, loopback only), two tabs: **En attente** (what the user must do: open questionnaires, trial entries to tick, « En traitement » (retours and « OK + idée » not yet settled), then folded « Traités » and « Testé et OK ») and **Suivi** (the six colours, paused issues, the last ten finished). Source: `scripts/suivi-page.html` (French, exempt from the French guard). The older online page is frozen and links here. Nobody writes the page by hand and no agent writes the state by hand: scripts only.

## The colour rule

An issue holds its colour while (a) the Claude session that owns it is alive, or (b) one of its questionnaires is open, or (c) one of its trial entries with a `try` field is still `todo`. Otherwise it is **paused**: colour free, worktree kept. On resume it gets its previous colour back if free, else the first free. "Held" is computed when read (a crash pauses by itself). `scripts/suivi.py status [--json]` (or `chantier.sh --status`) prints it; `check` lists inconsistencies and writes `control.json` (the page footer « Vérifié il y a … »). Any `set` erases `--wait`/`--waiting` unless it restates them. The card's line is computed: orange « À toi : … » from open forms, entries to tick and a `--wait you` note (joined with « · »), else grey: « L'agent travaille », « Agent à l'arrêt depuis N min » (hours above 60), « Session ouverte » (no activity data) or « En pause » (no line when the colour is held with no live agent, e.g. `legacy`). Any action only the user's hands can do (measurement, diagnosis, probe, install, machine step, trial) is an entry on the page (`suivi.py test add`, the command to run in `try`), never only a terminal message, even before any code (#483). `--wait you --waiting "…"` is a complement only (it turns the card orange and is erased by the next `set`; the page drops it as soon as the user has no open form, entry to tick or merge to launch left, or when it names an open form, #530) and never replaces a form or an entry: `set --wait you` is refused while the issue has no todo entry with `try` and no open form (`--force`, justified in the report). A note of kind `dep` or `ag` stays muted text. The step strip shows the stored state, except `questions` with a form of the issue finished and none open, shown as « Code » (`qcm_answered`, #530). The server reads the agent's activity by `stat` only (never the transcripts): the newest mtime of `~/.claude/projects/*/<session>.jsonl` and `*/<session>/subagents/*.jsonl`, as `agent_idle_min` in whole minutes (seam `SF_CLAUDE_PROJECTS`); 5 minutes or more reads as stopped. Limit: up to 5 minutes of lag, and a long silent command can read as stopped. Commands: `claim`, `set --state questions|code|essai|fusion --what … [--wait you|dep|ag --waiting …]`, `pause`, `done`, `release-line`, `check`.

## Decision forms, local (#441)

The start and follow-up forms are posed here, not published: `python3 scripts/suivi.py qcm pose <n> data.js --title "…"` (checks and counts the cards, creates `qcm/<n>-<k>/`, prints the id and `http://127.0.0.1:8441/qcm/<id>`). **One open form per issue** (#479): `qcm pose` refuses more than 8 cards (a list card counts as one), a malformed list card and code words in the card texts (#520, `--force` overrides each with one stderr line); it refuses while the issue has an open (unfinished) form and names it; a new batch is posed after the first one is finished (`463-1` then `463-2` stays allowed). `--force` overrides; name it after the data file (`suivi.py qcm pose <n> data.js --force`), because a `--force` before the number escapes the hook's pattern and the wait is not armed; justify it in the report. A shared form posed on issue A is not detected from issue B (known limit). `check` lists an issue with two open forms. **Withdrawing**: `suivi.py qcm withdraw <id> [--answered]` (only the session that owns the issue or its parent, like `test remove`; a finished form is never withdrawn; a form holding any answer, `Plus tard` included, needs `--answered`, which prints the answers) moves the whole folder to `removed-qcm/<id>/`, readable afterwards with `qcm answers <id>` (it says `withdrawn`); the user can do the same with « Retirer » on the form's box in « En attente » (always confirmed in the box, with the count of answers). A withdrawal from the page wakes the waiting agent once (`form <id> withdrawn on the page by the user, N answers recorded, read with: suivi.py qcm answers <id>`); one from the CLI wakes nothing. The form's tab then gets 410 and says « Questionnaire retiré ». **Answers of a withdrawn form are not asked again**: before posing a replacement, read them (`qcm answers <id>`) and reuse them in the new form. `qcm pose` prints one reminder line per withdrawn form of the issue holding answers, and refuses a card whose question title (whitespace and case ignored) was answered in one (`Plus tard` is not an answer); the tool only catches identical wording, so the check is yours; `--force` overrides. On a plain withdrawal with no replacement, only keep and read them.

The form appears in « En attente » with its progress; the user answers there (each answer is a file), then presses « J'ai fini » at the bottom of the summary, which sets `finished` and frees the colour unless something else holds it. Agents read the answers with `suivi.py qcm answers <id> [--json]` and list forms with `qcm list [--open] [--issue n]`. Template and card rules: `stokesforge-bug-report/references/decision-form.md`. After `qcm pose` the agent ends its turn: it is woken on the answers (§ The agent wakes). The published Artifact form stays as the fallback (user away from the PC, or asked).

## Trial checklist

(#423) Before asking for `scripts/try.sh <n>`, write the entries of a visible change in one go. The user does not guess what to test.

Entries are **guided routes**, at most 5 unmerged per issue (`test add` refuses beyond; `--force`, justified in the report). One entry is one story of 2 to 3 minutes. Group what only the user can judge into routes (look, gesture, feel, what the driver cannot show, see Pre-trial below); the detailed edge-case list (refusal and its message, `STOKESFORGE_LANG=en-XA` when texts changed) stays with the pre-trial agent, not in the entries. Routine steps (Ctrl+Z/Ctrl+Y, save and reopen) are not entries: automatic tests cover them (#518). Be didactic. Sibling issues are trialled in one round, one sheet per issue, each with its own `try`.

**Sheet pitfalls** (each one cost the user a trial; a flawed sheet looks like a bug): the `try` command opens a prepared project and can be rerun without losing anything (no destructive variant within reach of the up-arrow); no Python to paste unless only a script reaches the case (then say so); prove the sheet fails without the fix; one route is one window, and every button or field is located on screen ("bottom of the page, the field right of Graph 4"); for a web page write "browser tab" and give the link. A defect that makes a route unpredictable is fixed before the trial, not noted in the sheet. A new concept is explained in plain words in the chat before the entries. When redoing or adding entries, re-read ALL open entries of the issue against the latest commits and labels (`test remove` + `test add`), and say in the report which were redone and which only verified. While entries are open nobody edits that worktree (`try.sh` builds it as it is on disk); further work goes in a temporary worktree (`git worktree add -b tmp/<n>-x`) and is brought in after the answers. A step that needs the real machine is one command block for the user, no fake `systemctl` or simulation.

**Measurement entries (#483).** An action to do before any code (drag an image on a probe page, run a diagnostic) is an entry like the others with `"kind": "measure"` (the only value accepted), `steps` for the gesture, `expect` for what to report back, and the command to run in `try`. The page labels that command « Lance d'abord » instead of « Avant, lance (pas encore fusionné) ». Nothing else differs: it counts as an entry with `try`, holds the colour and wakes the agent when ticked.

1. Write a JSON file: one object, or a list, with `title` (« Parcours 1/3 (3 min) »), `goal` (#518, **required** on every entry with `try` except `kind: measure`: one line, shown as « On teste : … » above the route; it replaces the old `intro` prose), `around` (**required on at least one entry of the batch**, the series' last route: one line, shown as « Essaie autour : … » below « Tu dois voir »; `test add` refuses a batch without it), `where` (menu or window steps, English labels as on screen), `steps` (short French imperatives, each « gesture → what you must see »), `expect` (tick OK if every step showed it), `try` (`scripts/try.sh <n>`; `scripts/try.sh <n> <file.stf>` opens that project instead of the demo, as a fresh copy at every run, so the sheet can say « relance la commande » without losing anything; a missing file or a non-`.stf` is refused).
2. `python3 scripts/suivi.py test add <n> entries.json` creates `tests/<n>-<k>.json`, status `todo`.
3. The message to the user names the page and the number of entries; the terminal does not repeat the list. Ticks alone are not the go-ahead (§ The agent wakes, merge). After a « Retour », fix on the branch (a retour round runs the touched crate's tests and the workspace clippy only, no screenshots; a small fix with the user at the screen is a live touch-up, `.claude/skills/stokesforge-feature/SKILL.md` § 4. Test, look, document; #515) and redo the trial: `test remove <n> <id>... [--answered]` (only your own issue or its parent, never a merged entry; an answered entry needs `--answered`, its comment is printed back and named in your report; archived in `removed-tests/`), then `test add`. A retour fixed **without** a new trial is not removed but settled (#496): `suivi.py test settle <id> --commit <fix> --note "…"` (the fix commit on the branch, any commit of the repository). It leaves « En traitement » for the folded « Traités » (date, commit, note), keeps the user's comment and screenshots, and counts as OK for « Fusionner ». The user can do the same with « Classer » on an unsettled retour (settled `by: user`, no commit; this one wakes the wait like an answer, the agent's own settle wakes nothing). A new Retour or an OK from the page on a settled entry clears `settled`; a note keeps it. `scripts/deliver.sh` refuses while an entry of the issue is a retour nobody settled (`suivi.py test unsettled <n>` lists them, exit 1); `suivi.py check` also lists the unsettled retours of done issues or issues without a record.

   **« OK + idée » (#518).** A third tick on each card: OK plus a text (« Envoyer l'idée »), stored as `idea` on an `ok` entry. It never blocks: the entry counts as OK for « Fusionner » and `deliver.sh` only prints one line naming the unsettled ideas (`suivi.py test unsettled <n> --ideas` lists them, exit 0). It wakes the wait like a comment (wake line `<id> ok + idea: <text>`). The agent settles **each idea before delivering**: handle it now in the same issue when it is cheap and related, then `suivi.py test settle <id> --commit <fix>`; or later, `suivi.py test settle <id> --note "#N"` after opening a new issue. Avoid both a dragging issue and a full new cycle (scope, form, trial, merge) for a small idea. `test list` marks an unsettled idea `(idea)`, and `check` lists the unsettled ideas of done issues. A later status sent from the page drops the idea.
4. At the merge, `scripts/deliver.sh` runs `test merged <n> <commit>` (sets `commit`, removes `try`); it refuses a commit that is unknown, not on `main`, without the issue's branch while it exists, or not citing #<n>. A repeat with the same commit is « already recorded »; another commit needs `--replace <old>` (`test merged <n> <new> --replace <old>`). Any other usable change adds its entry after the merge with `test add` and a `commit` field. `test list [--issue n]` lists them (a settled one is marked `(settled)`). `test settle <id> [--commit HASH] [--note TEXT]` (#496) marks a `retour` as handled: status stays `retour`, `settled` is added; it refuses an entry that is not a retour or already settled, a commit unknown to the repository (any commit, it need not cite `#n`), and an issue owned by another live session (no claim needed otherwise); it wakes no wait and changes no count. A user screenshot (#456) appears as its own indented line `  image: <absolute path>` under the entry (`test list`), the card (`qcm answers`, and `image_paths` in `--json`) or the wake line: open that file to see it. A file the size limit deleted reads `  image removed by the size limit: <name>` (`images_removed_by_size_limit` in `--json`). `test remove` moves the screenshots with the entry to `removed-tests/<id>.images/` and prints `images archived: <path>`; an entry with only a screenshot counts as answered.

## The agent wakes (#454)

After `qcm pose` or `test add` the agent launches nothing and ends its turn; it never asks the user to say they finished. A `PostToolUse` hook of `.claude/settings.json` runs `suivi.py hook-wait` after any `suivi.py` call on an issue the session owns: it waits on local files and wakes the idle agent. After a wake the agent reads the answers (`qcm answers`, `test list`) and acts; any later `suivi.py` call on the issue re-arms the wait by itself. Without an active hook, fall back to `suivi.py wait <n>` as a background Bash command. Only the session that owns the issue arms.

- **Wake policy** (`should_wake`, the one place): a Retour, a comment on an OK, a finished form (« J'ai fini »), the result of a page-started merge (`delivered as <M>` or `delivery failed: <reason> (log <path>)`), the click itself (information only), a form the user withdrew on the page, or no `todo` left. A plain OK with entries left wakes nothing. A screenshot sent alone counts like a comment (attaching wakes nothing, only sending does). An OK + idea waits like a comment. A Retour or comment waits 180 s after the last change of any entry (`SF_SUIVI_WAIT_SETTLE`); a finished form, a merge result or no `todo` left wakes at once.
- **Merge** (#531): the page merges by itself; Claude's permission system is never involved. When every entry is OK (or a retour settled), the agent writes the merge message to a file (first line `Merge #<n>: …`) and stores it: `python3 scripts/suivi.py merge-message <n> <file> [--wait-tag rc|final]` (same checks as `deliver.sh`: the first line, no closing keyword and no `--wait-tag` on an integration line, no closing keyword with `--wait-tag`; it also stores the branch head and prints the unsettled ideas as a warning). Then it announces the merge is ready and ends its turn (the wait stays armed). Until then the card reads « L'agent prépare la fusion » and there is **no button**; with the message stored the card says « À toi : lancer la fusion » and shows « Fusionner » (« Fusionner dans <line> » on a line), or the user types « fusionne #n » in the terminal and the agent runs `scripts/deliver.sh` as before. A click makes `serve` start the delivery in a transient `systemd-run --user` unit (normal priority, outside the Nice=19 service; `deliver-run <root>` runs the main checkout's `scripts/deliver.sh` with the main checkout as cwd, the log in `deliver/<root>.log`); the card shows « Fusion en cours », then « Fusionnée » or « Échec : <reason> ». Exit 3 (main moved): the run reruns `scripts/test-all.sh` in the issue's worktree (« Tests relancés, puis fusion ») and delivers again, 3 deliveries at most; red tests or a branch head that moved after the preparation fail the run. Any later change of an entry before the launch voids the click: no run. The click wakes the agent only to inform it: **it must not run `deliver.sh`**. On `#<n> delivered as <M>` it cleans up (`scripts/chantier.sh --release`, the report). On `#<n> delivery failed: <reason> (log <path>)` it reads the log, fixes on the branch (rerun `scripts/test-all.sh`) and stores the message again: the button comes back only then (a store clears the failed state). A server killed mid-run does not lose the result (the run is its own process); a run whose process is gone reads « Échec » (interrupted). After a merge that changes `suivi.py`, restart the service (`systemctl --user restart stokesforge-suivi`) or the button gets a 404 from the old server. Not covered by tests: the real `systemd-run` start and the SSH push from the unit (BatchMode, `SSH_AUTH_SOCK` passed through); the first real click is their trial.
- **Card**: « L’agent écoute » / « il repart à ta réponse » (waiting), « écris-lui après ta réponse » (agent stopped), « Réponse reçue : lance #n » (paused, unread answer).
- **Safety net**: `hook-news` (SessionStart, UserPromptSubmit) prints unread answers; `chantier.sh` runs `suivi.py news <n>` on a claim. A wait never holds a colour.
- **Limits**: a closed terminal cannot be woken (the answer waits for the next `lance`); a real wait is not proven beyond a few minutes; the hook timeout is 72 h.

## Slowness seen at the trial (#474)

`scripts/try.sh` builds in debug by default (build time), and debug draws far slower than release (#340: about 23 frames/s against 120). When a trial reports a slowness, the agent first asks the user to rerun with `scripts/try.sh --release <n>` and to say how loaded the machine was (other builds, tests or apps running); it diagnoses only what survives in release.

## Pre-trial (#452)

Before `test add`, only when a gesture or a drawing changes (prompt template: [`stokesforge-feature/references/agent-prompts.md`](../../stokesforge-feature/references/agent-prompts.md)), a Sonnet agent (the pre-trial agent) works in the branch's worktree on the invisible screen (`run-stokesforge`):

1. It walks the detailed checks: each edge case of the start form, refusals and their messages, `STOKESFORGE_LANG=en-XA` when texts changed. It plays **every sheet literally** (each step as written, in order) before `test add`; for a drag or resize it plays the gesture and its reverse, with no modifier, then Shift, Ctrl, Alt. Undo/redo and save/reopen are the Rust tests' job (#518).
2. It fixes what it finds on the branch, reruns the tests, then **re-verifies the fix in the real app**. Only then the orchestrator writes the entries (`test add`) and asks for `scripts/try.sh <n>`: the user tests only what works.
3. The detailed list and the captures live outside the worktree (`../_stokesforge/<n>-pre-trial.md`): `chantier.sh --release` refuses untracked files.
4. The message to the user names what the driver cannot show: native Wayland, `rfd` file chooser, detached OS window, OS drag and drop, multi-screen, scale other than 1, real GPU look, and « is it what I wanted ».

**Agent screenshots are the agent's own internal check** (#455): never shown to the user on a card, as proof or as a comparison bank. The user always opens the app themselves.

The user's trial stays mandatory for a visible change; the pre-trial replaces none of it, and the orchestrator's own re-verification before the merge is not weakened. The limit of 5 entries is unchanged.

A retour **after** the merge becomes a GitLab issue through `stokesforge-bug-report`; then settle it: `test settle <id> --note "#N"` (#496).

## Notifications (W9)

`PushNotification` at three moments: start form ready, trial ready, tracking page updated. A form or a trial still notifies once; the user answers on the page, not in the terminal. The message starts with `<square> #<n>` and carries the local link `http://127.0.0.1:8441/`.

## Server

`scripts/suivi.py serve [--port 8441] [--state DIR]`: single-threaded `http.server` on 127.0.0.1 (exit 1 if the port is taken). `GET /` page, `GET /api/state` (aggregate, ETag), `POST /api/tests/<id>` (status, comment; needs header `X-Suivi: 1`, same-origin `Origin`, own `Host`; ids `[A-Za-z0-9_.-]+` not starting with a dot; body at most 256 KB). Screenshots: `POST /api/tests/<id>/images` and `POST /api/qcm/<id>/images/<code>` take the raw bytes (not JSON; type by magic bytes, 10 MB, answer `{name}`, no entry changes), `GET /api/tests/<id>/images/<name>` and `GET /api/qcm/<id>/images/<code>/<name>` serve them (strict name, server Content-Type, `Cross-Origin-Resource-Policy: same-origin`, a long private cache); an entry or card lists them with `images` in its POST, which deletes the unlisted files, and a save that omits `images` on a QCM card deletes the card's files. An old server answers 400 or 404 to an upload: restart it. `GET /qcm/<id>`  serves the form template with the QCM's `data.js` injected (404 if unknown), `GET /api/qcm/<id>/answers`, `POST /api/qcm/<id>/answer` (one card record) and `POST /api/qcm/<id>/finish` follow the same checks as the tests POST. The user installs it once with `scripts/suivi-install.sh` (user unit `stokesforge-suivi.service`, started with the GNOME session (`graphical-session.target`, like the dictation services) at the lowest CPU and I/O priority, system `/usr/bin/python3`; rerun it after a change of the script; `scripts/suivi-uninstall.sh` removes it and keeps `.suivi/`). The server keeps the code it started with: after a merge that changes `scripts/suivi.py`, run `systemctl --user restart stokesforge-suivi`. The page file is re-read at each request. A change to the CI watcher needs the same restart. `POST /api/issue/<n>/merge` (same guard; 409 unless every entry is OK and the agent stored the message, 409 after a ended run until the message is stored again, 200 and no second run on a repeated click) never waits: the run is a separate process started in a transient user unit (§ Merge), so it outlives the server; its seams for tests are `SF_SUIVI_DELIVER`, `SF_SUIVI_TESTALL` and `SF_SUIVI_DELIVER_LAUNCH=direct`.

## CI watcher (#452)

`serve` also runs a daemon thread that reads the CI of the newest commit of `main` about every 120 s, so nobody polls it by hand. The line "CI rouge / verte / en cours / inconnue sur main" sits above the tabs on both pages, and `/api/state` carries it as `ci` (`verdict`, `names`, `reason`, `sha`, `last_red`; never `checked_at`, which would defeat the ETag). The page file is the display; the verdict is computed by `scripts/suivi.py`:

- Jobs: `scripts/ci-status.sh --head` (the head of `main` read through `glab`, not the local clone). Linux and Windows jobs all come back as GitLab statuses (`JOBS` of `scripts/gitlab-status.py`, which includes `test-windows`, `test-python-windows`, `dist-windows`). Green only when every job of that list except `robustness` is present and SUCCESS. A FAILED job (Windows too) is red, with its name. No pipeline yet is pending, then unknown after an hour. CANCELED, a `glab` failure, a timeout, empty or unreadable output is unknown. Only a green verdict is final for a SHA; a red head is read again at each poll, since the CI may be re-run on the same commit.
- A red stays in `last_red` (shown while the new head is pending or unknown) until a newer head is green. The watcher sends no desktop notification: the page is its only signal.
- `ci.json` missing, corrupt, or older than 3 polls reads as unknown. The colour rule and the `pending` count do not depend on the CI.
- Seams for tests: `SF_SUIVI_CI=off` (no thread), `SF_SUIVI_CI_POLL`, `SF_SUIVI_CI_TIMEOUT`.
- Integration lines (#480): the thread also reads the head of each line (`ci-status.sh --head <line>`, `ci-line-<name>.json`); `/api/state` carries `lines` = {line: CI view + `issues` declared on it, delivered or not}. The page shows one row per line under the CI line of `main`; a red line never colours `main`. The record field `line` (absent = `main`) is read by `suivi.py line <n>`; `line-trial <issue> <line>` and `line-clear <line>` serve `scripts/line.sh land`. The `line-*` worktrees are not work-package worktrees: `status` and `check` ignore them. The label `ligne-<line>` is the user's: it is not in `LABEL_ALL`, the label pass never touches it.

## Build modes (#476)

A row under the CI line sets how builds behave on this PC: « FullIA » (user away, no CPU cap), « Développement » (user at the PC, work keeps moving), « Arrière-plan » (builds really limited), plus a checkbox « Auto » (off by default: battery gives « Arrière-plan », 10 minutes without input gives « FullIA », otherwise the chosen mode). One sentence under the buttons describes the effective mode from the `MODES` table of `scripts/cargo-queue.py`, where all the numbers live; a second line names the running build and how many wait. A build typed by the user in a terminal (tty, no `CLAUDECODE`) skips the wait but is listed as running. FullIA also puts the PC in the `performance` power profile on mains (the sentence says so) and puts the previous profile back on leaving, unless the user changed it meanwhile; on battery the found profile is put back (and `performance` is set again within one 30 s tick when mains returns; the user's own change always wins), and a profile that cannot be read, set or put back shows as one grey line (`profile_note` of `build_queue`, a code of `profile.json`). Without the installed shim the row is one grey line naming `scripts/cargo-queue-install.sh`; a stale installed copy adds a warning to rerun it.

`/api/state` carries `build_queue` (`{"installed": false}` when absent; start timestamps, never durations, so the ETag holds). `POST /api/build-mode` takes `{"mode": "full|dev|background"}` and/or `{"auto": true|false}` behind the same guard as the other writes (400 unknown mode or bad body, 409 not installed) and applies the slice limits at once, also to running builds. A build keeps the job count (`jobs` of the mode) it started with; only weight, memory, quota and affinity change live. `serve` runs a 30 s thread for Auto only on the real state (seam `SF_SUIVI_BUILD_AUTO=on|off`); the same thread puts a left-over power profile back. In tests the profile link is off whenever `SF_CARGO_QUEUE_DIR` is set and a canary `busctl` on PATH must stay unused: never the real profile. After a merge that changes `suivi.py`, restart the service to get the control.

## GitLab labels and tag report (#467)

`serve` runs a second thread (about 120 s, state `labels.json`) so the GitLab issue list shows where each issue stands. It runs **only for the real state folder**: with `SF_SUIVI_DIR` or `--state` it stays off unless `SF_SUIVI_LABELS=on` (`off` forces it off), so no test can write to GitLab.

- **`en-cours` / `en-pause`**: same reading as the page (`held_by`): a live owner, an open form or a trial to tick with no agent, or `legacy` is `en-cours`; a record that holds nothing is `en-pause`; done, unstarted or no record is none. A package parent is `en-cours` while one of its sub-issues is held; a paused sub beside a held sibling is `en-pause`. The tracking state wins: a hand edit is undone at the next pass. Held to paused waits 10 minutes (`SF_SUIVI_LABELS_SETTLE`, seconds) so a `/clear` does not flap; promotion, done and closure are immediate. A closed issue loses every label of ours and is not labelled again; reopened, it is.
- **Waiting labels**: `attente-rc` (an `-rcN` or the final tag proves it) and `attente-final` (final tag only). The label alone is the membership, so a hand-placed one works. A waiting label hides `en-pause`; `en-cours` stays if an agent resumes. The service adds one only for a `tag-wait` declaration (once) and removes them at closure.
- **Writes**: one `PUT` per changed issue with `add_labels` / `remove_labels` (never `labels=`, which replaces the user's labels) and, for a closure, `state_event=close`. Reads per pass: the issues carrying each of our four labels, then the record numbers by `iids[]`, all `state=all`. Any failed, timed-out or empty read writes nothing and tries again at the next poll; the page and `/api/state` do not change (ETag).
- **Tags**: the service reads `repository/tags` on GitLab each pass (never `releases`: an `-rcN` release is created then deleted). The first run only records what exists. At a new tag, each open issue with a label that tag handles (an rc tag: `attente-rc`; a final tag: both) gets a comment with its job results and, unless a job failed or lacks proof, a card in « En attente » (a trial entry without `try`: it holds no colour). The card OK closes the issue and drops both labels in one `PUT`; Retour keeps it open. A failed job: comment, label kept, no card. A later tag gives a new comment and card; never two for the same tag and issue, restart included (`tags.json`).
- **Job results** come from the GitHub public API (`actions/runs?event=push&branch=<tag>`, no token, 60 requests per hour, read every 10 minutes while a tag is undecided; seams `SF_SUIVI_TAGJOBS_API`, `SF_SUIVI_TAGJOBS_POLL`, `SF_SUIVI_TAG_CAP`) and `pages` from the GitLab pipeline of the tag. Only the run of the tag's own commit counts. A job missing, still running, skipped or unreadable (403) is no proof; a running job or an unreadable GitHub delays the report (6 h at most). A matrix job (`name (leg)`) is ok only if every leg succeeded; a failed step of a `continue-on-error` job counts as failed. A hand-placed label has no declaration: all release jobs are reported and the card says « relis l'issue » (and still gives the hand route to the files).
- **Tag cards (#497)**: the card lists each file of `--files` (`exe`, `tar.gz` = the Linux archive only, `rpm`, `deb`, `manual`) with the direct link `https://gitlab.com/askrzypczak/stokesforge/-/package_files/<id>/download` read from the generic package `stokesforge` at exactly the tag's version (GitLab's filter is fuzzy: `third-party-licenses` also comes back; a repeated file name takes the highest id), the package page, the hand route (Deploy → Package registry → `stokesforge` at the version, not `third-party-licenses`; Deploy → Releases only on a final tag) and the steps. The job that builds a needed file joins the issue's jobs (`exe` `dist-windows`, `tar.gz` `release-linux`, `rpm`/`deb` `upload-linux-packages`, `manual` `release-manual`), so a failed builder gives the comment and no card. The registry is read before the comment is posted; unreadable, it retries at each poll and after the 6 h cap the card carries the predictable generic URLs. A file absent from a readable package: the card goes out with « ⚠ … absent du registre ». The service downloads the card's files to `~/Downloads/StokesForge-<version>/` (skips a file of the same size, `.part` then rename, a failure is a warning on the card; off for tests and `tag-check`: `SF_SUIVI_DOWNLOAD=on|off`, `SF_SUIVI_DOWNLOAD_DIR`). A jobs-only proof says « Rien à faire à la main : le job X est vert, coche OK. ».
- **Declaring**: `suivi.py tag-wait <n> rc|final [--jobs a,b] [--step "gesture → what you see"]… [--files exe,tar.gz,rpm,deb,manual] [--human "…"]` (`--step` repeatable, `--human` is one more step, a step without « → » earns one warning; a bad `--files` kind exits 2 and writes nothing; a call that gives steps or files replaces the earlier ones), or `deliver.sh --wait-tag`, then the label appears within about 2 minutes.
- **By hand**: `suivi.py labels sync [--dry-run]` runs one label pass (`--dry-run` prints the `PUT`s and writes nothing); `suivi.py tag-check <tag> --dry-run` reads GitLab and GitHub and prints what the service would report for that tag, writing nothing: run it before a tag. `suivi.py tag-check <tag> --card <n> [--files k]` prints the JSON card the service would make for issue n (GETs only, no download) to show a sample on the tracking page. `suivi.py status` ends with the last sync (time, ok or failed with the reason) and the issues that wait.
- **Restart rule**: the service is a user unit; after changing `scripts/suivi.py` restart it (`systemctl --user restart stokesforge-suivi.service`, see `scripts/suivi-install.sh`), else the old code keeps running.

## Migration and `legacy`

`python3 scripts/suivi.py migrate` creates records from the old colour files and `.packages`. Sessions started before the migration have no owner on record, so every migrated issue that still has a worktree (and every package with a colour) gets `legacy: true`: it counts as held until the issue is claimed (`chantier.sh`), paused or done. The page shows it with « état à confirmer par sa session ». `import-online <out_dir>` copies the `tests/*` documents of an `ArtifactData list … out_dir` export of the old online page into `tests/` once (idempotent; a local entry is never overwritten; unsafe ids are rejected).

## Work packages and worktrees (#413, #419)

- A task's worktree lives in `../_stokesforge/feature<n>` (a folder beside the main checkout, `<n>` = the issue number), created by `scripts/chantier.sh <n>` from an up-to-date `origin/main` (branch `feature/<n>-<topic>`, no upstream tracking). Never a `StokesForge-<n>` folder beside the checkout, nor the harness folder `.claude/worktrees/`. The orchestrator creates it and hands its path to the implementing agent instead of `isolation: "worktree"`. One worktree per issue, one session.
- `scripts/chantier.sh <n>...` is run by the orchestrator in the current session, from the main checkout (the user types `lance #<n>` in plain `claude` or after `/clear`); it starts no session, prints a briefing and is idempotent. The user launches in plain words, with or without a number; the orchestrator finds the issue or package, runs `chantier.sh` when the match is clear and asks only when in doubt (#420). Rule: `.claude/skills/stokesforge-feature/SKILL.md` § 1
- A work package with sub-issues: `lance #<parent>` makes `chantier.sh` detect the open sub-issues that name the parent (`Parent: #<n>` first; older forms stay recognised). It creates no worktree for the package itself: the sub-issue list and order are the second card of the single start form, then `scripts/chantier.sh <parent> --start <sub-issue>` creates one worktree per sub-issue, all in the package's single colour (the parent's record; between two sub-issues the package keeps it only while a session owns the parent; `scripts/chantier.sh --done <parent>` ends it after the last merge). The tag is `<square> #<parent> › #<sub> <name>`.
- Several orchestrators may run at once. The colour tag `<square> #<n> <short name>` that `chantier.sh` prints (first free of 🟦🟩🟧🟪🟥🟨) starts **every message** of an orchestrator working on a package (every tag when it holds several issues), so the user tells parallel terminals apart without reading (#418); it is also used in decision forms, the tracking page and notifications. One colour per **issue**, shared by all its worktrees (`feature426`, `feature426b`…), kept in one record per issue in `../_stokesforge/.suivi` (never edit it by hand; rule: "The colour rule" above).
- The colour is freed for good by `scripts/chantier.sh --release <n>` (refuses an issue with no trial entry unless `--no-trial`, removes the merged, clean worktree and its branch, prints one line to copy in the report); `--pause <n>` pauses any issue or package, `--done <parent>` ends a package. `scripts/suivi.py status` (or `chantier.sh --status [--json]`) lists the six colours, who holds them and why; `suivi.py set` records the state at each change; `suivi.py check` lists inconsistencies. The `SessionEnd` hook of `.claude/settings.json` only speeds up pausing; `SessionStart` and `UserPromptSubmit` (`suivi.py hook-news`, always exit 0) hand an owning session the answers it has not read, or tell a new session which issues hold a colour (#454).
- Merges happen only in the main checkout, under the `main` lock, through `scripts/deliver.sh` (`stokesforge-verification` step 6); `scripts/try.sh <n>` opens a branch on the user's screen (for `main`, `cargo run -p stokesforge-app` is the same).

## Template target (#523)

New worktrees start from a copy of a build of `main` (`scripts/template-target.sh`, section Local build queue of docs/tests.md). Machine step, for the user to run once (add it as a trial entry with `suivi.py test add`, never only a terminal message):

```sh
scripts/cargo-queue-install.sh                       # the shim must know the `low` class
scripts/template-target.sh refresh                   # first template, about 50 min at 2 jobs; the log goes to the terminal
scripts/template-timer-install.sh                    # weekly prune of paused worktrees and size check
```

`chantier.sh` may wait up to 900 s for the template lock while a refresh runs (`SF_TEMPLATE_WAIT_S`): run it in the background then, since the 10-minute Bash cap killing the copy is the usual cause of a leftover `.target-copying/` (#528). That folder is ignored by git; a rerun of `chantier.sh`, the next copy and the weekly prune remove it unless a copy still holds its lock; `template-target.sh status` reports it.

After that `deliver.sh` refreshes the template by itself at every merge to `main`. `scripts/template-target.sh status` shows commit, size and whether a refresh runs.
