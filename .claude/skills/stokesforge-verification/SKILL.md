name: stokesforge-verification
description: Verify a StokesForge change before delivering it — test in the right place, fmt, clippy, tests, python feature, docs, English commit message. Use on « teste » (test), « vérifie » (verify), « c'est bon ? » (is it good?), « commit », « pousse » (push), « j'ai fini » (I'm done), and at the end of any implementation or fix.
---

A green `cargo test --workspace` does not prove what one assumes in this repo. This skill says what it does not prove.

## Steps

1. **Place the tests**: unit, integration, robustness, app logic, painted gesture, witness, reproduction: [references/test-placement.md](references/test-placement.md). Value bar for any new test: `audit-test`.
2. **Run the base checks** of `CLAUDE.md` § Commands (`fmt --check`, `clippy -D warnings`, `scripts/test-all.sh` (nextest when installed, else `cargo test --workspace`), `python3 scripts/french-guard.py`). **Retour rounds (#515)** run only `cargo nextest run -p <touched crate>` plus always the same `cargo clippy --workspace --all-targets -- -D warnings` (never `-p` for clippy: slower and a different feature set, measured 94 s against 28 s warm). `scripts/test-all.sh` runs once, on the commit to deliver: on a clean tree and green it writes the stamp `<git common dir>/sf-tested/<sha>` that `deliver.sh` requires. Long output goes to a file, only the summary is shown; heavy cargo runs in the background because it may wait in the local queue (#476, `docs/tests.md`) (`CLAUDE.md` § Delegation and model choice); reread the file instead of rerunning. In Claude's container a heavy test can fail with `Disk quota exceeded` (`/tmp`): that proves nothing about the code. Put `TMPDIR` on disk (`docs/tests.md` § Using CI day to day), or ask the user to run `! cargo test …`; never merge first.
3. **Run what the change adds**: `python` feature, ignored reproductions, targeted recalculation, licenses, screenshots, a real window: [references/checks-by-change.md](references/checks-by-change.md). A change to a workflow script (`scripts/chantier.sh`, `try.sh`, `deliver.sh`…), even a briefing text, runs `scripts/workflow-test.sh` before the commit (#464: a briefing grew past its line bound and `main` went red). A slowness reported at a trial: ask for `scripts/try.sh --release <n>` first ([references/suivi.md](references/suivi.md), "Slowness seen at the trial"). A task that touches an off-default feature compiles and tests it explicitly, or it validates dead code.
4. **Reread the diff**: `git status --short`, then `git diff`; never carry the user's untracked files or work in progress into a commit: `git add <path>` one by one, never `-A`, and say so when a changed file does not come from the task. No test weakened, no architecture guard bypassed (`docs/tests.md` § Guards not to break), arbitrated limits still in place.
5. **Update the docs the change made wrong**: the module `//!` (the *why*), the `docs/` page (the *what*); the user manual `manual/src/` if the change is visible (its screenshots are regenerated by `scripts/deliver.sh` at the merge, not before, #515); routing files (`.claude/rules.md`, `CLAUDE.md`, `.claude/rules/`) if paths, scripts or boundaries moved; the skills concerned if a new rule was installed, in the same commit.
6. **Commit on the branch freely; merge and push by the rule below.** Work on `feature/<n>-<topic>`, merged into `main` with `--no-ff` (commit "Merge #N: … (Closes #N)"), never squashed nor rebased once shared. Message in English (since #368; the older history is French): `<domain>: <imperative verb> <object>` (`stokesforge-app: align window actions`), `Closes #<n>` for a fixed issue. `main` is pushed by `scripts/deliver.sh` (below), which refuses a branch head without a test stamp (run `scripts/test-all.sh` on the clean branch, then rerun) and refuses while a trial entry of the issue is a retour nobody settled: a retour fixed without a new trial is settled first with `suivi.py test settle <id> --commit <fix> --note "…"` (#496). No merge request unless asked. CI results of a commit: `scripts/ci-status.sh [commit]` (`docs/tests.md` § Using CI day to day). **Never create or push a `v*` tag** without the user's explicit order: a tag starts the publication.
   - **Merge rule (#413).** Green (all tests run, even for a script or doc change) and **not visible** (no screen, gesture or text the user would see): merge and push `main` without asking. **Visible**: a pre-trial agent first walks the detailed checks in the real app and fixes what it finds ([references/suivi.md](references/suivi.md), Pre-trial section); then the trial checklist goes on the tracking page **before** the user is asked to run `scripts/try.sh <n>` (a few guided routes, `suivi.py test add`, `.claude/skills/stokesforge-verification/references/suivi.md` § Trial checklist); the agent wakes on the user's answers and, once all entries are OK, announces it is ready and merges on the user's go-ahead, the « Fusionner » button or their word in the terminal (`references/suivi.md` § The agent wakes); ticks alone do not merge. A « Ça ne va pas » is fixed on the branch, then the entry is redone (`test remove`, then `test add`: § Trial checklist).
   - **Sequence, one orchestrator at a time on `main`**, from the main checkout (`git status --short` clean first, else stop): write the merge message to a file (first line `Merge #<n>: …`) and run `scripts/deliver.sh <n> <message-file>` **in exactly that standalone form** from the main checkout (the `permissions.allow` rule `Bash(scripts/deliver.sh *)` of `.claude/settings.json` matches only that text; a compound command, a `cd` or an env prefix needs approval) (lock, merge, push with retries, release the lock, `test merged`). Exit 0 delivered; 1 failed, lock released, fix and rerun; 3 `main` moved and was merged into the branch: rerun `scripts/test-all.sh` (the head changed, the old stamp no longer covers it), then rerun `deliver.sh`. Before the lock it also regenerates the manual screenshots when the branch touches the interface or the build (`crates/`, `assets/`, `manual/screenshots.json`, `Cargo.lock`) and commits the changed images onto the branch. It stops before `chantier.sh --release`: close and release as below, no CI polling (next bullet). A held lock is waited for or reported, never broken.
   - **Integration line (#480).** Work that must not reach `main` yet goes on a long-lived line branch. An issue whose record has `line` (label `ligne-<line>`, `suivi.py line <n>`) is delivered the same way, into the line: `scripts/deliver.sh <n> <message-file>` works in `../_stokesforge/line-<line>` (clean, on the line), the main checkout may be dirty or elsewhere. The message says `Refs #<n>`: a closing keyword or `--wait-tag` is refused, since the issue closes only when the line lands (`scripts/line.sh land`). A branch of `main` that holds a line-only commit is refused. Exit 3 = the line moved and was merged into the branch. The trial of the whole line is `scripts/try.sh <line>`; its entries are `suivi.py test add 480` with `"try": "scripts/try.sh <line>"`, and `line.sh land` waits for all of them to be OK. `main` reaches the line by `scripts/line.sh sync <line>` (a regular merge, never the other way); `scripts/line.sh create <line>` opens one (then restart the `stokesforge-suivi` service). Details: `docs/v1-criteria.md`, `docs/tests.md`.
   - **Never `git stash`** in a worktree (#424): the stash stack lives in the common `.git`, so with parallel worktrees one `pop` takes another task's changes. Set work aside with a commit on the branch (amend or reset later) or `git diff > file`.
   - **Weekly toolchain check (#412).** `.github/workflows/toolchain-weekly.yml` (Monday, stable and beta, informative, blocks nothing) runs the depth-cap tests in release mode and, on beta, the workspace tests and clippy. Read it with `scripts/toolchain-weekly-status.sh` (public GitHub API, no `gh` needed; the failed log is on the run page it prints); a red run means a new compiler changed something, to fix in the code. Slow tests carry the `slow::` marker: `cargo test -- --skip slow::` skips them for a quick local pass.
   - **No CI polling.** The orchestrator reports at the merge, closes and releases without waiting for the CI; the watcher of `suivi.py serve` shows red on the tracking page. A package's next sub-issue does not wait. Still read the CI (`scripts/ci-status.sh`): for a tag or release, and for a change to CI itself. A newer push cancels the running series (`ci.yml` concurrency): read the CI of the newest `main` that contains your commit (`git merge-base --is-ancestor`). A red `main` is reported and fixed first, whoever broke it.
   - **Trial cards for a tag**: one direct link per built file (GitLab generic package `stokesforge/<version>`, `.../-/package_files/<id>/download`, never "GitHub Actions"), the files in `~/Downloads/StokesForge-<version>/`, the command already tried (Ubuntu 22.04: toolbox `sf-ubuntu2204`, `essai-ubuntu-22.04.sh`), and "nothing to do, tick" said when a CI job is enough. Reread the generated cards before announcing them. A dictated « tag » is a GitLab label or a version tag: write which one in full.
7. **Close the issues the diff settles**: list them, put `Closes #<n>` in the commit (« Refs » closes nothing) or `glab issue close <n>` with a comment citing the commit, then check with `glab issue view <n>`. Report which issues are closed and which stay open. An issue that stays open **only because a tag proves it** is declared at the merge: `scripts/deliver.sh --wait-tag rc|final <n> <message-file>` (`rc` if an `-rcN` or the final tag proves it, `final` if only the final tag does; refused when the message says `Closes #<n>`; add `suivi.py tag-wait <n> rc|final --jobs a,b --human "…"` first to name the jobs and what the user checks by eye). The service then puts the label `attente-rc` / `attente-final` on the GitLab issue and, at the next tag, comments with the job results and posts a card to tick (OK closes the issue). `chantier.sh --release` warns when an issue is left open with no declared wait. Details: `.claude/skills/stokesforge-verification/references/suivi.md` § GitLab labels and tag report.
8. **Record what landed**: a visible change already has its trial entries: `deliver.sh` ran `test merged <n> <merge commit>` (§ Trial checklist for a correction); any other change that is usable gets its entry now (`suivi.py test add`); a retour that came after the merge and became a GitLab issue is settled with `test settle <id> --note "#N"`; the cleanup below marks the issue done; run `python3 scripts/suivi.py check`; notify the phone with the local link: [references/suivi.md](references/suivi.md).
9. **Report** three things without rounding: what changed, the checks **actually run** (not planned), the validation limits. A failing test is reported with its output; a skipped step is said. **Last line (#462), once merged, closed and released:** the user should not have to ask whether the conversation can go. Nothing left in this session (no open question, no « Retour », no next sub-issue, no other issue held): say in the interaction language that everything is done and `/clear` is safe. Something left: name it instead, without offering. Only the user can run `/clear`; never offer it before the merge.

## Clean up after a merge on `main`

For an issue on an integration line (#480) read "the line" for `main`: `scripts/chantier.sh --release <n>` tests the merge against the line (the main checkout may be on any branch), deletes the branch from the line worktree and does not warn that the issue stays open. Landing the line and closing its issues is `scripts/line.sh land`, not this cleanup.

After a merge on `main` and a successful push to `main`, remove the task's temporary worktree **and its local branch** without waiting to be asked; removing a worktree does not delete its branch.

Session hygiene (#517): after a merge the user types `/clear` (the last line of the report says when it is safe, step 9); a session that stays idle between packages is woken with `/clear` + `lance #<n>`, never resumed with its whole context.

- From the main checkout on `main`, run `scripts/chantier.sh --release <n>` (`<n>` or `<n><letters>` for a second worktree such as `426b`). It checks, before removing anything, that the branch is merged into `main`, that the worktree has no modified or untracked file and no ignored file other than `target/` and `__pycache__/` (it lists them and refuses otherwise), and that the issue has at least one trial entry (`scripts/suivi.py test add`; `--no-trial` for a change with nothing to try, said in the report), then removes ONE worktree (`git worktree remove`, no `--force`) and its merged branch (`git branch -d`, never `-D`). Keep any undelivered work; untracked or modified files that block it are shown to the user, who decides. List the task's open sub-agents and its `backup-*` branches too.
- **Copy the one line it prints into the report** (`Couleur 🟦 libérée.` or `Couleur 🟦 reste prise : <reason>`): the colour is shared by every worktree of the issue; the reason is another worktree, an open QCM, a pending trial, or the package parent that a session still owns. When it says « libérée » the issue is marked done.
- Anything that stops while waiting (the user, another work package): `scripts/chantier.sh --pause <n>` (any issue or package) drops the owner, frees the colour unless a QCM or a trial still holds it, and keeps worktrees and the sub-issue list; the next `lance` or `--start` takes the previous colour back if free, else the first free. A crash or `/clear` pauses the same way, by itself (`scripts/suivi.py`, #441).
- After the last sub-issue of a package has merged and its worktree is released (or when the parent closes), run `scripts/chantier.sh --done <parent>`: it marks the package done, prints `Couleur <square> libérée.` and refuses while a worktree of the package still exists (#419).
- Confirm neither remains and include the cleanup in the report; if it blocks, give the precise cause and keep what is left to deliver.

Only the finished task's temporary resources: never other work's branches or remote branches without an explicit request. A request to keep the worktree or the branch wins.

Done when the base checks and every check the change requires ran with their real result stated, the diff holds only the task's files, and the docs the change made wrong are updated.
